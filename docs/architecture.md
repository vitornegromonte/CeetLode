# CeetLode Architecture and Product Specification

## Objective

CeetLode is a browser-based code-review practice app. A user reads a supplied solution, explains what the code does, proposes an optimization, and compares both responses with curated rubrics and a reference answer.

The MVP is for one local or self-hosted developer, has no accounts or leaderboards, and does not use AI for grading or feedback.

## Assumptions

- The first release is a browser SPA accessed locally or on a private network.
- The frontend and API are separate applications.
- Frontend, FastAPI, PostgreSQL, and Redis run through Docker Compose.
- Data is persisted in PostgreSQL.
- PostgreSQL is the only database implementation targeted by the MVP.
- FastAPI exposes the application API and SQLAlchemy/Alembic manage database access and migrations.
- Redis stores replaceable draft submissions; it is not an authoritative data store.
- Redis drafts expire after seven days and have their expiry refreshed whenever the draft is saved.
- Initial curated exercises use Python source code.
- The initial five-exercise dataset covers two-sum/pair lookup, nested-loop optimization, binary search, stack validation, and sliding window problems.
- JavaScript is used for React application code; TypeScript is not introduced in the MVP.
- Reference answers and rubric data are curated by maintainers and can be stored in the repository or database.
- Python dependencies and virtual environments are managed with uv.
- JavaScript dependencies and scripts are managed with Bun.
- Property-based tests are required at domain boundaries where generated inputs can expose edge cases.

## Technology Decisions

| Area | Choice | Reason |
|---|---|---|
| Frontend framework | React 18+ with Vite | Suitable for a rich SPA without server-side rendering |
| Frontend language | JavaScript | Reduces frontend tooling and learning burden |
| Frontend package manager | Bun | Fast local installs and script execution |
| Styling | Tailwind CSS | Responsive utility-first styling with a consistent design system |
| Routing | React Router | Handles exercise, submission, and history screens |
| Server state | TanStack Query | Loading, caching, errors, retries, and refetching |
| Code display/editor | CodeMirror 6 | Syntax highlighting and read-only code presentation |
| Backend framework | FastAPI | Clear Python API structure and automatic OpenAPI documentation |
| Python environment and dependencies | uv | Reproducible environments and dependency management |
| Database | PostgreSQL | Strong relational constraints and mature local/self-hosted tooling |
| Draft cache | Redis | Fast, replaceable storage for draft submissions |
| Backend ORM | SQLAlchemy 2 | Relational mapping and migration integration |
| Migrations | Alembic | Reproducible PostgreSQL schema changes |
| API validation | Pydantic | Request and response validation |

## System Architecture

```text
Browser (React/Vite)
  |  HTTP JSON
  v
FastAPI
  |-- SQLAlchemy --> PostgreSQL
  |-- Redis client -> Redis
```

The frontend must not access PostgreSQL directly or contain secrets.

The backend must own exercise, rubric, submission, and progress data. Static public exercise metadata may be shipped in seed data, but submission and progress state must use API endpoints.

## Domain Model

The MVP needs these core entities:

- `Exercise`: title, summary, Python source code, and difficulty.
- `Rubric`: 3-6 ordered checklist items, each with a title and expected observation.
- `ReferenceAnswer`: explanation and optimization proposal.
- `Submission`: the submitted explanation and optimization text for one exercise attempt.
- `SubmissionRubricMatch`: user-selected rubric items covered by a finalized submission.
- `Progress`: exercise completion status and timestamps derived from submissions.

Submission fields are immutable after finalization. Every finalized attempt is retained as a separate PostgreSQL submission record. Draft fields are stored in Redis and may be overwritten. Saving a final submission creates a new immutable PostgreSQL submission record and invalidates the matching Redis draft.

## API Responsibilities

The API provides:

- Exercise listing, filtering, and detail retrieval.
- Rubric retrieval for an exercise.
- Draft creation and update.
- Final submission creation.
- Reference-answer reveal after final submission.
- Exercise progress retrieval.
- Database health reporting.

The API should use RESTful resource routes and Pydantic schemas. The OpenAPI document is generated by FastAPI and is available at `/docs` only in development or private deployment environments.

Example resources:

```text
GET    /api/exercises
GET    /api/exercises/{exercise_id}
GET    /api/exercises/{exercise_id}/rubrics
GET    /api/exercises/{exercise_id}/draft
PUT    /api/exercises/{exercise_id}/draft
DELETE /api/exercises/{exercise_id}/draft
POST   /api/exercises/{exercise_id}/submissions
GET    /api/submissions/{submission_id}
GET    /api/submissions/{submission_id}/reference-answer
GET    /api/progress
GET    /api/health
```

## Frontend Structure

```text
frontend/
  AGENTS.md
  src/
    app/           -> Router, providers, layout
    components/    -> Reusable accessible UI
    features/
      exercises/   -> Exercise list and detail
      workspace/   -> Code and response workspace
      submissions/ -> Submission and reveal states
      progress/    -> Progress UI
    hooks/         -> Reusable React hooks
    lib/           -> API client and shared utilities
    styles/        -> Tailwind entry and global styles
  tests/
    unit/
    integration/
    e2e/
```

Initial routes:

```text
/                         -> Exercise library
/exercises/:id            -> Exercise workspace
/submissions/:id          -> Submitted review and reference comparison
/progress                 -> Local progress overview
```

The workspace separates code context, explanation, optimization proposal, and actions into visible sections. It must handle loading, empty, saved-draft, submitted, and reference-reveal states.

## Backend Structure

```text
backend/
  AGENTS.md
  app/
    api/routes/      -> FastAPI routers
    api/dependencies/
    core/            -> Configuration and shared application setup
    models/          -> SQLAlchemy models
    schemas/         -> Pydantic schemas
    services/        -> Use-case orchestration
    db/              -> Session and migration setup
  migrations/
  tests/
    unit/
    integration/
  seed/
```

Keep route functions thin. Put database queries and use-case rules in services or repositories rather than in route handlers.

## Testing Strategy

Backend tests use pytest:

- Unit tests for validation and domain rules.
- Integration tests for API routes and PostgreSQL persistence.
- Migration upgrade/downgrade smoke tests.
- Hypothesis property-based tests for normalization, validation, text invariants, filtering, and submission rules.

Property tests must run with bounded example counts and use explicit shrinking. Seed a fixed random seed in CI when deterministic reproduction is preferred, and retain failing examples so they can become normal regression tests.

Frontend tests use Vitest and Testing Library:

- Component behavior and form state.
- Loading, error, empty, draft, submitted, and reveal states.
- API integration tests for key React Query flows.
- fast-check property-based tests for pure helpers, form transformations, filtering, sorting, and state transitions.

Browser-level Playwright tests cover:

- Opening an exercise.
- Saving a draft.
- Finalizing a response.
- Revealing the rubric and reference answer.
- Returning to the exercise library.

Responsive UI verification at 320px, 768px, 1024px, and 1440px is required.

## Boundaries

- **Always:** Keep secrets outside source control, validate API input with Pydantic, use migrations for schema changes, preserve draft history, and run relevant tests.
- **Ask first:** Adding dependencies, changing the database schema, changing exercise data formats, or adding authentication.
- **Never:** Commit credentials, implement AI grading in the MVP, expose the database to the browser, remove a failing test, or weaken submission validation to bypass errors.

### React Implementation Rules

- Do not use `useEffect` for state synchronization or data flow.
- Derive state during rendering, use event handlers, or subscribe to external stores instead.
- Do not use imperative timers to synchronize React state or mask architecture mismatches.
- Do not add comments that justify quick fixes, workaround patches, or architectural hacks.
- Implement declarative React patterns that pass linting and static analysis without suppressions.

### FastAPI Implementation Rules

- Do not call blocking I/O inside `async def` routes. Use async-native clients and drivers, or use a standard `def` route for thread-pool execution.
- Keep database access and business or ML pipeline logic out of routers.
- Routers may import only service interfaces and Pydantic schemas.
- Do not add comments, `# type: ignore`, or `# noqa` patches to bypass correctness or static analysis.

## Success Criteria

- A user can browse and open a curated exercise.
- The MVP ships with five curated Python exercises.
- A user can save and restore a draft for an exercise.
- A user must provide both an explanation and an optimization proposal before final submission.
- Final submissions reject drafts unless both text fields contain at least 20 non-whitespace characters.
- A final submission prevents silent mutation of its saved text.
- After submission, the user can view the rubric and reference answer.
- Progress reflects finalized submissions and survives backend restarts.
- The frontend and backend run separately using documented local commands.
- The API has an available OpenAPI document and passing integration tests.
- Core frontend flows pass component and browser tests.
